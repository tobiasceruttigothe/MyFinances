# Análisis 360 — 2026-06-09

Auditoría completa del proyecto (código, k8s, seguridad, funcionalidad) hecha al cambiar el
objetivo de AWS a **VPS con k3s** ([[decision-vps-en-vez-de-aws]]). Lo marcado ✅ se **arregló
en esta sesión**; lo demás es backlog priorizado.

## Arreglado en esta sesión

| # | Hallazgo | Fix |
|---|---|---|
| 1 | **Spoofing de `X-User-Id`**: el filtro del gateway usaba `mutate().header()`, que *agrega* el header sin pisar el del cliente. `@RequestHeader` downstream toma el primer valor → un usuario autenticado podía leer/escribir datos de otro mandando `X-User-Id: <uuid-víctima>`. | ✅ `headers.set(...)` pisa siempre; en rutas públicas se *elimina* cualquier `X-User-Id` entrante. `JwtAuthenticationFilter.java` |
| 2 | **CORS hardcodeado** en `CorsConfig.java` (solo localhost) — bloqueaba el dominio del VPS. | ✅ Property `cors.allowed-origins` (env `CORS_ALLOWED_ORIGINS`), default localhost. Env agregado a `gateway-service.yaml` |
| 3 | **Postgres sin PVC**: ni `postgres-db` ni `keycloak-db` montaban volumen → **todos los datos se perdían al recrear el pod**. | ✅ PVCs `postgres-data` (2Gi) y `keycloak-db-data` (1Gi), `PGDATA` en subdir, `strategy: Recreate`, probes `pg_isready` |
| 4 | **Sin probes ni resources** en ningún manifiesto (salvo n8n) → K8s no sabía si un servicio estaba vivo; un pod colgado seguía recibiendo tráfico. | ✅ readiness+liveness (`/actuator/health`) y requests/limits en los 7 servicios |
| 5 | **`target/` trackeado en git** (39 archivos .class) y sin `.gitignore` raíz. | ✅ `.gitignore` creado, `git rm --cached` (queda staged) |
| 6 | Objetivo AWS obsoleto en CLAUDE.md / vault. | ✅ [[decision-vps-en-vez-de-aws]] + CLAUDE.md + [[overview]] + [[deployment-infra-plan]] |

> Para deployar los cambios: `./rebuild.sh gateway-service` + `./deploy-k8s.sh`. La primera vez
> que se aplique `postgres.yaml` con PVC la base arranca vacía (los datos actuales eran efímeros
> de todas formas) — re-correr el seed/Newman.

## Backlog priorizado

### P0 — Seguridad (antes de exponer nada al dominio público)

- **Credenciales hardcodeadas en manifiestos**: `myfinances_pass`, keycloak `admin/admin`,
  keycloak-db `password` están en texto plano en `k8s/*.yaml` versionados. Moverlas a Secrets
  no versionados (mismo patrón que `intake-secrets.yaml`) y rotarlas en el VPS.
- **Keycloak corre en `start-dev`** (`keycloak.yaml`): modo dev explícitamente no apto para
  producción (sin HTTPS estricto, caches dev). Para el VPS: `start` + `KC_HOSTNAME` +
  `KC_PROXY=edge` detrás del túnel/ingress.
- **HMAC del webhook de Meta** sin validar en n8n (`X-Hub-Signature-256`) — pendiente conocido
  de [[whatsapp-audio-intake]]; obligatorio con URL fija pública.
- **`/actuator/**` whitelisted en el gateway** — expone health/info/env de todos los servicios
  sin auth. Restringir a `/actuator/health` o sacarlo del whitelist público en el VPS.
- **`GET /api/v1/users/by-phone/{phone}`** pasa por el gateway con cualquier JWT válido →
  cualquier usuario logueado puede mapear teléfonos→userId. Debería ser solo interno (sacarlo
  del route del gateway o exigir un header interno).
- **Rotar credenciales pegadas en chats** (PAT GitHub, key Anthropic, token Meta, key ElevenLabs)
  — pendiente desde 2026-06-07.

### P1 — Para que el deploy a VPS funcione

- **Registry de imágenes**: `imagePullPolicy: Never` no existe en un VPS. Publicar imágenes a
  **GHCR** desde CI (GitHub Actions: build multi-stage ya existe) y cambiar los manifiestos a
  `image: ghcr.io/tobiasceruttigothe/<svc>:<tag>` + `imagePullSecrets`.
- **Footprint de RAM**: 7 JVMs + Keycloak + 2 Postgres + n8n + zipkin ≈ 6–8 GB. Para un VPS de
  4 GB: bajar `-Xmx` (256m alcanza), apagar zipkin, o consolidar (¿goals dentro de account?).
- **Backups**: CronJob `pg_dump` diario + copia fuera del VPS (rclone a Drive/B2). Sin RDS no
  hay red de seguridad.
- **Config-server depende de GitHub** en runtime: si GitHub no responde en el arranque, el
  cluster no levanta. Mirror local (`spring.cloud.config.server.git.basedir` persistente +
  `cloneOnStart`) o migrar a ConfigMaps.
- **Frontend no tiene deploy**: hoy solo `npm run dev`. Falta imagen nginx (multi-stage con
  `npm run build`) + manifiesto + ruta en el ingress/túnel.
- **Versionar el vault**: `Vault-Myfinance/` y `frontend/design_handoff_my_finances/` están
  **fuera de git** — un disco roto pierde toda la memoria del proyecto.

### P2 — Calidad de código

- **Tests**: goals-service, intake-service y gateway tienen **0 tests**; los JUnit de
  user-service están rotos (pre-existing, [[bug-refresh-token-snake-case]]). El fix del
  gateway (spoofing) merece un test de integración que mande `X-User-Id` falso.
- **Paquete inconsistente**: `com.myfinances.gateway_service` (snake_case) vs
  `com.myfinances.user`. Cosmético, pero molesto.
- **`PendingConfirmationStore` en memoria** (intake): se pierde al reiniciar el pod; con >1
  réplica se rompe. Redis o tabla Postgres cuando importe.
- **CI inexistente**: ni build ni lint en GitHub Actions. Mínimo: `mvn package` de los 7 +
  `npm run build && npm run lint` en cada push (y de paso publica imágenes a GHCR → P1).

### P3 — Funcionalidad (de [[future-features-wishlist]] + nuevas)

- Fase 3 outbound (Workflow B: código de verificación por WhatsApp) + token permanente Meta.
- Fecha en lenguaje natural en el intake ("ayer", "el lunes") — hoy todo es "ahora".
- Gastos recurrentes con ajuste por inflación AR (wishlist #2) — encaja como scheduler en
  account-service, mismo patrón que [[concept-scheduling-goals]].
- Neto (ingresos − gastos) visible en dashboard (wishlist #1).
- Multi-moneda (ARS/USD) — hoy las transacciones no tienen campo currency; en Argentina es
  casi obligatorio. Requiere migración de schema, decidir antes de tener muchos datos.
- Export CSV/Excel de transacciones (cierra el loop "mis datos son míos").

## Roadmap VPS sugerido (orden)

1. P0 completo en local (secrets, keycloak `start`, HMAC, actuator, by-phone).
2. CI GitHub Actions → imágenes en GHCR (P1).
3. Probar k3s en el server casero (notebook vieja) con los mismos manifiestos — barato y reversible.
4. Contratar VPS (≥4 GB con footprint ajustado; cómodo con 8 GB), k3s, Named Tunnel
   `myfinances.qzz.io`, deploy frontend incluido.
5. Backups + monitoreo básico (Uptime Kuma o similar) → recién ahí invitar usuarios reales.
